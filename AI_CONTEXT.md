# AI Context — Behavioral Rules & Project State

This file is the companion to [`CLAUDE.md`](./CLAUDE.md). Where `CLAUDE.md` is the map (what exists, where to find it), this file is the rulebook for _how to act_ on this specific project, plus the state that only exists because of this project's decision history — not derivable by reading the docs cold. General coding hygiene (naming, TypeScript strictness, comment discipline) lives in [`docs/AI_RULES.md`](./docs/AI_RULES.md) and is not repeated here.

---

## Workflow conventions established on this project

- **Documentation changes and code changes are separate approval gates.** Approval to update docs, or to produce a plan, is not approval to write application code, run installs, or scaffold frameworks — even immediately after a plan was approved. Always get an explicit, separate go-ahead before the first line of actual code.
- **Architecture-affecting proposals get an ADR**, not just a prose edit — see `docs/ADR/`. If you're about to change something that already has an ADR, that's a signal to stop and confirm with the user rather than silently overriding it.
- **Verify third-party tool claims before they inform a decision.** ADR-002 (two databases instead of one shared schema) exists because an initial design was checked against Payload CMS's actual documentation/issue tracker and turned out to rely on an experimental, bug-prone feature. Don't take a library's capability on faith when a real architectural decision depends on it — check the source.
- **When a request conflicts with something already frozen, say so and ask — don't quietly comply or quietly refuse.** Surface the tension (as was done for the Vercel/VPS deployment split below) rather than resolving it unilaterally.

## Absolute constraints

- Never replace or suggest replacing **Payload CMS**, **NestJS**, **Prisma/PostgreSQL**, or **pnpm + Turborepo**. These are frozen (see `CLAUDE.md` and ADR-001/002/003).
- Never introduce or reference **Sanity CMS**, or any CMS other than Payload.
- Never use Payload's `schemaName` adapter option to share a database with Prisma — two independent databases (`sam_platform`, `sam_cms`) is the frozen decision (ADR-002).
- Never let `apps/web` call Payload's API directly — NestJS is the only API surface the frontend talks to (ADR-003). **This includes the Admin Dashboard**, which is an area inside `apps/web`, not an exception: it calls `/api/v1/admin/*` only, never Payload, never a database.
- Never create a fourth application. The Admin Dashboard lives inside `apps/web` as a separate route area (`app/(admin)/admin/*`, outside the `[locale]` segment) — approved decision; `apps/admin` was explicitly rejected.
- Don't add speculative infrastructure or abstractions for future phases (Customer Portal, CRM, Workflow, ERP Integration, AI/RAG, etc.) beyond what `docs/DATA_MODEL.md §2` already anchors. Future-phase design happens when that phase starts, not now.
- If AI/RAG capabilities are ever built, they must never query `sam_platform`/`sam_cms`/MinIO directly — only through the existing NestJS API, and RAG's own vector store must be its own isolated database, never grafted onto an existing one. Full rationale: `docs/ai/RAG_ARCHITECTURE.md §0`.

## How to re-orient in a fresh session with no conversation history

1. Read `CLAUDE.md`, then this file.
2. Check `docs/ROADMAP.md`'s "Current Status" for what phase the project is actually in right now (this file's own status notes above may lag if bootstrap has since happened — trust `ROADMAP.md` over this file for current state, and update both if you're the one moving the project forward).
3. Read `docs/ADR/README.md` for the decision log before proposing anything that touches monorepo tooling, database topology, API integration, or CMS boundaries — those four already have a settled answer.
4. If asked to do something that seems to contradict a frozen decision, cite the ADR and ask before proceeding.
