- ✅ **Consent-version persistence (`sam_platform`)** — the second of the two conditions the Privacy Policy ordering names, closed on 18 August 2026. **Schema:** migration `20260818120000_add_consent_privacy_policy_version` adds one nullable `TEXT` column, `privacy_policy_version`, to `inquiries` and `custom_formulation_requests` — additive, transactional, no index, no other table touched, no data written, `sam_cms` untouched. Both tables were empty in local DEV before and after. **Backend:** the value is the constant `ACTIVE_PRIVACY_POLICY_REVISION` in `apps/api/src/modules/forms/privacy-policy-revision.ts`, written by both services on insert. **Option chosen: code-owned, not CMS-read, not client-supplied, not environment-supplied.** A Payload lookup in the write path would let a CMS outage reject a valid lead and would rest the record on `Pages.lastUpdatedDate`, an editor-set display field; a client-supplied value is not evidence of anything; an environment variable would leave no history of which revision was in force when, whereas changing a constant is a commit. Neither DTO declares the field, so sending it answers **400 naming the property**, exactly as `status` does. **API surface is unchanged** — still `201` with `data: { id, createdAt }`, and the column is never returned. **The constant is `null`, and stays `null` until approved policy content exists**: no revision identifier was invented, nothing was backfilled, and the identifier's eventual format is a legal/product decision left to the gate that publishes the policy. **Immutability is PostgreSQL's, not the application's:** a follow-up migration, `20260818140000_privacy_policy_version_immutable`, installs a `BEFORE UPDATE` trigger on both tables that rejects any change where the column `IS DISTINCT FROM` its stored value — `NULL` to a revision, a revision to `NULL` and a revision to another revision all fail, while `NULL` to `NULL`, an unchanged value and every other column proceed. **No privileged bypass exists and none may be added**, so a consent recorded against `NULL` can never be rewritten to claim a policy was in force; the triggers are `ENABLE ALWAYS`, so `session_replication_role = replica` does not skip them (measured). Re-checkable with `scripts/verify-consent-version-immutability.sh` — 19/19 assertions pass and every probe row is rolled back. **Consent links remain inactive**
  — condition 1 (approved, published, legally reviewed policy content) is still open, so nothing in the UI changed and no consent label gained a link.

Forms are progressive-enhancement `<form action>`, with six states kept distinct (idle · submitting · success · field errors · rate limited · API unavailable / unexpected error); field messages are keyed by the API's own `details[].field`, so there is no client-side schema to drift. A rejected submission — validation, outage or rate limit alike — **keeps what was typed**: React 19 resets an uncontrolled form after any completed action, so the submitted values are echoed back and the controls remounted. **Sample and quote flows carry Product context**: the Product Detail CTAs link with `?product={slug}`, the route resolves the slug server-side into the `Product` id and name, and the submission stores `relatedProductId` — which is exactly what that column was added for. **Rate limiting:** both write endpoints enforce §Rate limits' **5 submissions per hour per client**, via `@nestjs/throttler` (the one dependency this gate added). The budget is **shared across the two paths**, because the contract budgets an endpoint group; exceeding it answers 429 `RATE_LIMITED` in the standard envelope with `Retry-After`. **No global guard is registered**, so every public GET is untouched and reads keep no limit at all — asserted by test, not by intention. Storage is **in-process**, which is correct for ADR-005's single-container topology and only for it. **No Redis, and no CAPTCHA** — see the blockers below.

Two consequences remain: the leads captured before it are permanently unattributable, and the column records `null` until the constant names a real revision, which happens when point 1 is closed. **This was the input that blocked the consent links specifically; the links stay inactive because point 1 does not.**

- **~~Consent records carry no policy version.~~ Closed 18 August 2026 — the mechanism exists; the value is still empty.** `Inquiry` and `CustomFormulationRequest` now carry `privacyPolicyVersion`, a nullable server-owned `TEXT` column written on insert from the constant `ACTIVE_PRIVACY_POLICY_REVISION` in `apps/api`. The shape decision that was "not decided and must not be guessed" is made and recorded: **one immutable revision string per submission** — not a CMS revision id, not a cross-database reference, not a consent-history table, and never client-supplied. **`Pages.lastUpdatedDate` is still not consent evidence** and is not read at submission time; nothing in the write path touches Payload, so a CMS outage cannot cost a lead. **What remains is content, not schema:** the constant is `null` because no approved Privacy Policy exists, so submissions still record "no versioned policy was in force" — which is accurate, and stops being the answer the day approved policy content is published and the constant is set in the same gate. Leads captured before this migration remain unattributable and nothing was fabricated to make them look otherwise.
- **Contact details unconfirmed.** The reason five of Contact Us's seven sections do not render.
- **~~A documented required-field conflict on `CustomFormulationRequest`.~~ Resolved as a docs correction, with no schema change.** The seven NOT NULL columns — `companyName`, `country`, `industry`, `email`, `productOrApplication`, `requiredSpecifications`, `consentGiven` — are the operational persistence contract; the API and the form require all seven. SITE_STRUCTURE §5 and [DATA_MODEL_GAP_REVIEW.md](./DATA_MODEL_GAP_REVIEW.md) §1 each now carry a current-schema correction. No migration was made and none is proposed.
