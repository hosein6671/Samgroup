- ✅ **Internal lead notification (SMTP)** — the first outbound path the platform has, closed on 18 August 2026, and the resolution of half of [API_CONTRACT_FINAL.md](./API_CONTRACT_FINAL.md)'s Remaining Blocker §4. **Zero schema change**: no `notifiedAt`, no `deliveryStatus`, no retry counter, no notification table, no migration — the gate's own preference, and nothing forced otherwise. **Mechanism: SMTP relay via `nodemailer` (9.0.5)**, the one dependency added, chosen over an HTTP transactional provider precisely because that would have required a commercial-account decision and a verified sender domain, neither of which exists. **Nothing is emailed to the buyer**, and the success copy is unchanged and still claims nothing: "Your inquiry has been received".

  **The delivery semantics are the point of the gate.** A submission is validated, persisted, and its `201` payload composed _before_ any mail is attempted; the notification is then awaited and **cannot change the outcome**. `LeadNotificationService` catches every failure — refused connection, rejected credential, rejected recipient, TLS failure, timeout, and a bug in the template builder alike — and turns it into one structured log line. **A lead is never lost to a mail failure**, which was the frozen principle this gate had to satisfy. The attempt is **awaited rather than detached**: a floating promise would answer sooner and be silently dropped whenever the process is replaced mid-request, and doing it properly asynchronously needs a queue and a durable delivery record, which is a separate architecture gate. The cost is latency, **bounded at 5 seconds** by nodemailer's per-phase timeouts _and_ an overall cap — measured at 5.09 s against a relay that accepts the connection and then stalls, with the lead persisted and `201` returned in both that case and a refused-connection case (0.08 s).

  **Configuration is entirely environmental, with no defaults and no mailbox anywhere in the code**: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_SECURE`, `MAIL_FROM`, `LEAD_NOTIFICATION_TO`, all optional, following the same optional-upstream convention `PAYLOAD_INTERNAL_URL` established. **Unconfigured is a supported state**, and it is the current one: the API boots, forms persist, and the attempt is skipped with the missing variable names logged. A **partial** configuration is treated as unconfigured rather than attempted — including `SMTP_USER` without `SMTP_PASSWORD` — so a half-finished environment fails as one clear line rather than once per submission. **No real value is committed**; the production mailbox, relay and credential are still the client's to supply.

  **The notification boundary is narrow by design**: `SmtpMailer` is the only file in the platform that imports nodemailer, `LeadNotificationService` is the only class permitted to decide a mail failure does not matter, and the controllers know about neither. Swapping SMTP for an HTTP provider later is one file and its spec, with the Forms services, the endpoints and the API contract untouched.

  **Injection safety is structural rather than filtered**: the notification type has **no `html` field**, the transport sets no `html` part, and the body is plain text — so a `<script>` in a submitter's message is inert wherever it is read, and is also not mangled, which matters because a Sales Expert needs to see what was actually sent. Subjects are built from a closed label map mirroring SITE_STRUCTURE §10's wording (via `apps/web`'s `inquiry-vocabulary.ts`), so **no submitted value reaches a header at all**; CR/LF is stripped from the subject anyway, to keep that true of future edits. **Product context is the id only** — `relatedProductId` is printed as it is stored, and no `ProductsService` lookup was added merely to enrich an email.

  **Logs carry the submission id, the notification kind, `mechanism=smtp` and an error class/code, and nothing else** — no name, company, email address, message body, recipient mailbox, or credential. **`SMTP_PASSWORD` never appears in any log or error message**, asserted by test rather than by intention.

  **Verified end-to-end** against a throwaway Node-core SMTP sink (no dependency, no Compose service, nothing committed): all four flows — General Inquiry, Request a Quote, Sample Request, Custom Formulation — produced **exactly one** `text/plain` notification each, with the approved field mapping, a literal `<script>` payload intact, and product context present as an id. Rate limiting is unchanged (5/hour shared across both endpoints, 429 with `Retry-After` on the sixth). All 12 verification rows were deleted afterwards; `inquiries` and `custom_formulation_requests` are both back to 0 in local DEV.

  **Not built, and stated as such:** no buyer acknowledgement, no `Reply-To` header, no retry, no queue, no scheduler, no Redis, no delivery-status persistence, no admin read path, no CAPTCHA, and no notification for the four submission entities that have no endpoint yet. Newsletter double opt-in, form acknowledgements and download links still have no mail path — what they lack now is operational (a mailbox, a relay, a sender domain) rather than architectural.

Not a JWT (a self-validating refresh token needs a revocation list to be revocable) and not argon2id (nothing to slow down against 256 CSPRNG bits, and a salted hash cannot be an indexed lookup key). **Rotation on every refresh**, in one transaction: the presented session is revoked and exactly one replacement created, and the presented token is dead immediately. **Concurrent refresh has exactly one winner** — a conditional `UPDATE ... WHERE revoked_at IS NULL AND expires_at > now AND <user is active>` requiring one affected row, relying on PostgreSQL READ COMMITTED re-evaluating the predicate against the committed row; **no in-process lock and no Redis**, so it survives a second container. Proven against a real database, not mocked: 6 simultaneous refreshes of one token produced 1 success and 5 generic 401s, with exactly one usable session left. **Logout revokes one session, scoped to the authenticated caller**, answers **204**, and is idempotent; presenting another account's token revokes nothing. **No access-token deny-list** — the access token stays valid for its remaining 15 minutes, unchanged at HS256/`sub`-only. **`UserStatus` is `active`/`disabled` and nothing else**: a disabled account cannot log in (with the same message and the same argon2 work as a wrong password — the status check runs _after_ verification), cannot refresh, and **fails its very next authenticated request**, because the guard re-reads `sam_platform` every time. **Disabling is permanent revocation, not suspension** — the correction this gate took after security review: `active → disabled` revokes every live session and stamps a credential cutoff (`users.credentials_revoked_at`) in one transaction, both enforced by **database triggers** rather than by a service, because there is no status-management endpoint and every transition today is a direct `UPDATE`. Re-enabling restores login and nothing else: a pre-disable refresh token and an unexpired pre-disable access token both stay refused forever. The cutoff can never be cleared or rewound — the database refuses the `UPDATE`. The Admin shell still admits the `admin` role alone, so the web surface is **narrower than the API** by design. **One wiring fix in Identity**, found by a real boot rather than by a test: Nest constructs a class-referenced enhancer in the module that declares the controller, so `IdentityModule` now also exports `JwtModule` and `UsersService` as the guards' construction dependencies — with a test asserting no module outside `identity/` names `UsersService`, so the widened export cannot become a second data path. **84 new backend tests and 83 new `apps/web` tests**; 783 and 201 in total, all passing, with the public submission path, its notifications and its rate limits untouched. **No dependency added.** Verified against a running API and a production `next build`: all four roles, no-token and garbage-token; ordering, paging past the end and the type filter; all four detail views; unknown id 404, malformed id 400, out-of-scope 404; an API outage rendering unavailable rather than a fake 404; every browser request to the `apps/web` origin and none to NestJS; and no token, cookie name or API origin anywhere in the rendered HTML or in web storage. **The verification rows were removed afterwards** — `inquiries`, `custom_formulation_requests`, `users` and `auth_sessions` are all back to 0, and the Product/Blog demo data is untouched.

A Sales Expert with nothing assigned gets the ordinary empty state, never a refusal. **Launch blockers created or sharpened by the lead-generation slice** — none of them is an implementation gap that this gate chose to skip, and each needs a decision rather than code:

- **~~No rate limiting on the public write endpoints.~~ Implemented** at the contracted 5/hour. Two conditions remain, neither of which this gate may settle: the counter is **in-process**, so a second `apps/api` instance would mean two independent budgets and an effective 10/hour, and a restart resets it — **multi-instance deployment requires a shared store and a revisit**; and the client is identified by `req.ip`, which behind ADR-005's nginx resolves to the **proxy's** address unless `trust proxy` is configured, collapsing every client into one bucket. `trust proxy` is deliberately not enabled here: setting it without knowing the proxy depth makes `X-Forwarded-For` client-writable and the limit trivially bypassable, which is the worse failure. It belongs with the VPS work, and the VPS does not exist.
- **No anti-spam.** SITE_STRUCTURE §10 and §Rate limits both specify an **invisible** captcha, never a visible challenge. **No provider is selected and none is implemented**, and selecting one is an infrastructure decision rather than an implementation one. **Rate limiting does not satisfy this requirement** — it bounds volume from one address and does nothing about a distributed or low-volume bot. Invisible CAPTCHA remains a production/launch security requirement.
- **No email.** Nothing acknowledges a submission and nothing notifies anyone. Recorded in API_CONTRACT_FINAL's Remaining Blockers §4 and now load-bearing: a lead that arrives is a row nobody is told about.
- **No Privacy Policy.** Every consent checkbox names a policy that has no page and no approved legal text; SITE_STRUCTURE's Outstanding Confirmations lists it as blocking the contact form from lawfully collecting data at all. The consent labels deliberately **do not link** — a 404 beside a consent box is worse than plain text — so there is no broken privacy link in the UI, and no placeholder page pretending to be a policy.

  **Three of the original four inputs are now closed and one is not.** Payload exists; as of 17 August 2026 the canonical route exists and reads it; as of 18 August 2026 `sam_platform` persists the consent version (see both entries above). The blocker is no longer technical in any part. What remains cannot be produced internally:

  1. **Approved policy content**, drafted and legally reviewed. Until it is published in Payload under the slug `privacy-policy`, the canonical route answers 404 in every locale — by design, and the correct behaviour while the page genuinely does not exist.
  2. **Human-reviewed `en`/`fa`/`ar` legal content.** Payload's `fallback: true` will serve English text under `/fa` and `/ar` the moment an English page is published, and the page labels that as untranslated — but **a fallback is not a legal translation**, and the platform must not be described as compliant in `fa` or `ar` on the strength of one.
  3. ~~**Policy-version persistence**, so a stored consent can be tied to the text it was given against.~~ **Closed 18 August 2026** — `privacyPolicyVersion` exists on both entities and is written server-side on every submission (see the gate entry above). Two consequences remain: the leads captured before it are permanently unattributable, and the column records `null` until the constant names a real revision, which happens when point 1 is closed. **This was the input that blocked the consent links specifically; the links stay inactive because point 1 does not.**

- **~~Consent records carry no policy version.~~ Closed 18 August 2026 — the mechanism exists; the value is still empty.** `Inquiry` and `CustomFormulationRequest` now carry `privacyPolicyVersion`, a nullable server-owned `TEXT` column written on insert from the constant `ACTIVE_PRIVACY_POLICY_REVISION` in `apps/api`. The shape decision that was "not decided and must not be guessed" is made and recorded: **one immutable revision string per submission** — not a CMS revision id, not a cross-database reference, not a consent-history table, and never client-supplied. **`Pages.lastUpdatedDate` is still not consent evidence** and is not read at submission time; nothing in the write path touches Payload, so a CMS outage cannot cost a lead. **What remains is content, not schema:** the constant is `null` because no approved Privacy Policy exists, so submissions still record "no versioned policy was in force" — which is accurate, and stops being the answer the day approved policy content is published and the constant is set in the same gate. Leads captured before this migration remain unattributable and nothing was fabricated to make them look otherwise.
- **Contact details unconfirmed.** The reason five of Contact Us's seven sections do not render.
- **~~A documented required-field conflict on `CustomFormulationRequest`.~~ Resolved as a docs correction, with no schema change.** The seven NOT NULL columns — `companyName`, `country`, `industry`, `email`, `productOrApplication`, `requiredSpecifications`, `consentGiven` — are the operational persistence contract; the API and the form require all seven. SITE_STRUCTURE §5 and [DATA_MODEL_GAP_REVIEW.md](./DATA_MODEL_GAP_REVIEW.md) §1 each now carry a current-schema correction. No migration was made and none is proposed.
